Principios con notación matemática y ejemplos en código Java  ·  Basado en el repositorio arielhurtado/SOLID

📐 Notación Formal

Definiciones
  • E = { e₁, e₂, … } — Elementos (clases, módulos)
  • Δ = { δ₁, δ₂, … } — Drivers de cambio (razones para cambiar)
  • cd(e) ⊆ Δ — Drivers que afectan a e
  • D ⊆ E × E — Dependencias (eᵢ, eⱼ) ∈ D
  • inh(e₁, e₂) — e₁ hereda de e₂
  • comp(e₁, e₂) — e₁ compone a e₂
  • Pre(m) — Precondición de un método
  • Post(m) — Postcondición de un método
  • Inv(c) — Invariante de la clase c
  • I — Conjunto de interfaces (I ⊆ E)
Axioma 1 Abstracción

“Programa para una interfaz, no para una implementación”

∀ cliente c ∈ E, ∀ implementación impl ∈ E | (c, impl) ∈ D
∃ abstracción a ∈ I // a oculta los drivers de impl
tal que cd(a) ⊂ cd(impl) ∧ (c, a) ∈ D ∧ (a, impl) ∈ D

El cliente c depende de la abstracción a, que encapsula los drivers de la implementación.

Axioma 2 Composición sobre herencia

“Favorece la composición frente a la herencia”

Dadas inh(e₁, e₂) y comp(e₁, e₂),
preferimos comp si ∃ a ∈ I | cd(a) ⊂ cd(e₂) ∧ (e₁, a) ∈ D

La composición permite depender de una abstracción, reduciendo el acoplamiento a los drivers del componente.

Teorema Central IVP — Principio de Variación Independiente

“Los elementos con los mismos drivers de cambio pertenecen juntos; los elementos con diferentes drivers pertenecen separados.”

∀ e₁, e₂ ∈ E :
cd(e₁) ∩ cd(e₂) ≠ ∅ → e₁ y e₂ deben estar en el mismo módulo
cd(e₁) ∩ cd(e₂) = ∅ → e₁ y e₂ deben estar en módulos separados

✔ Equivalencia lógica con SOLID: IVP ⇔ (SRP ∧ OCP ∧ LSP ∧ ISP ∧ DIP)

Definición Formal de LSP con Invariante

Dado inh(s, t), donde s es subtipo de t, se debe cumplir:

Inv(t) ⇒ Inv(s)  // La invariante de la base se mantiene en el subtipo
Pre(ms) ≤ Pre(mt)  // Precondición no más fuerte
Post(ms) ≥ Post(mt)  // Postcondición no más débil

Intuición: Un subtipo puede relajar la precondición y fortalecer la postcondición, pero nunca puede debilitar la invariante de la clase base.

🔹 SRP — Responsabilidad Única

❌ Síntoma Factura_Symptom

Violación: La clase Factura tiene 3 drivers de cambio diferentes:

cd(Factura) = { δ₁ (reglas de negocio), δ₂ (tasas impositivas), δ₃ (persistencia) }
|cd(Factura)| = 3  // Viola SRP: debería ser 1
// Factura.java — versión con síntoma public class Factura {
    public double calcularTotal() { // δ₁ ... }
    public double calcularImpuestos() { // δ₂ ... }
    public void guardarEnBD() { // δ₃ ... }
}

Δ = 3 Razones para cambiar — cualquier cambio en impuestos o en la base de datos obliga a modificar Factura.

✅ Solución Factura + CalculadoraImpuestos + RepositorioFactura

Solución: Separar responsabilidades en clases especializadas. Cada clase tiene 1 driver de cambio.

cd(Factura) = { δ₁ }  |  cd(CalculadoraImpuestos) = { δ₂ }  |  cd(RepositorioFactura) = { δ₃ }
|cd(c)| = 1  // Cada clase tiene una única razón para cambiar
// Factura.java — solo lógica de negocio public class Factura {
    public double calcularTotal() { ... } // δ₁
}

// CalculadoraImpuestos.java public class CalculadoraImpuestos {
    public double calcular(Factura f) { ... } // δ₂
}

// RepositorioFactura.java public class RepositorioFactura {
    public void guardar(Factura f) { ... } // δ₃
}

Δ = 1 por clase — cada clase cambia por una única razón.

🔸 OCP — Abierto/Cerrado

❌ Síntoma Store (con switch por país)

Violación: La clase Store debe modificarse cada vez que se añade un nuevo país. El driver de cambio δ₁ (nuevos países) fuerza una modificación en la clase.

cd(Store) = { δ₁ (nuevos países), δ₂ (cambios en tarifas) }
|cd(Store)| = 2  // Viola OCP: no está cerrada a modificación
// Store.java — versión con switch public class Store {
    public double calculateDeliveryCost(Order order) {
        switch (order.getCountry()) {
            case COLOMBIA: return 10.0;
            case MEXICO: return 15.0;
            case PERU: return 12.0;
            // ... más países
        }
    }
}

Δ = 2 Razones para cambiar — añadir un país o cambiar tarifas implica modificar Store.

✅ Solución IDelivery + Factory

Solución: Usar una interfaz IDelivery y una fábrica. La clase Store queda cerrada a modificación y abierta a extensión.

cd(Store) = { δ₂ (cambios en tarifas) }  — cerrada a nuevos países
cd(BoliviaDelivery) = { δ₁ (nuevos países) }  — abierta a extensión
// IDelivery.java — interfaz public interface IDelivery {
    double calculateCost(Order order);
}

// ColombiaDelivery.java — implementación concreta public class ColombiaDelivery implements IDelivery {
    public double calculateCost(Order order) { return 10.0; }
}

// Store.java — sin cambios al añadir un nuevo país public class Store {
    private IDelivery delivery;
    public double calculateDeliveryCost(Order order) {
        return delivery.calculateCost(order);
    }
}

Δ = 1 en Store — ahora solo cambia por cambios en tarifas. Nuevos países se añaden como nuevas clases.

🔹 LSP — Sustitución de Liskov

❌ Síntoma SpecializedTruck extiende Truck

Violación: SpecializedTruck permite modificar el odómetro directamente, violando la invariante de Truck.

Inv(Truck) : odometer ≥ 0 // El odómetro nunca debe decrecer
Inv(SpecializedTruck) : odometer puede ser modificado directamente // ❌ Viola la invariante
// Truck.java — clase base public class Truck {
    private int odometer;
    public void drive(int miles) {
        if (miles > 0) { // Pre: miles > 0
            odometer += miles; // Post: odometer aumenta
        }
    }
    public int getOdometer() { return odometer; }
}

// SpecializedTruck.java — subtipo que viola LSP public class SpecializedTruck extends Truck {
    public void resetOdometer() {
        odometer = 0; // ❌ Violación: permite decrecer el odómetro
    }
}

Δ = 1 Invariante rota — SpecializedTruck no puede sustituir a Truck sin alterar el comportamiento esperado.

✅ Solución Trip + SpecializedTruck con composición

Solución: Usar composición en lugar de herencia. SpecializedTruck contiene un Truck y delega, respetando la invariante.

Inv(Truck) : odometer ≥ 0 ✓ Se mantiene
comp(SpecializedTruck, Truck) // Composición en lugar de herencia
// Trip.java — abstracción que usa Truck public class Trip {
    private Truck truck;
    public void start(int miles) {
        truck.drive(miles); // Delegación
    }
}

// SpecializedTruck.java — usa composición public class SpecializedTruck {
    private Truck truck; // Composición
    public void doSpecialTask() {
        // No se puede modificar el odómetro directamente
    }
}

Δ = 0 Invariante respetada — SpecializedTruck ya no hereda, por lo que no viola LSP.

🔸 ISP — Segregación de Interfaces

❌ Síntoma IRepository (interfaz gorda)

Violación: La interfaz IRepository tiene métodos para User, Project y Task. Cada servicio depende de métodos que no usa.

cd(IRepository) = { δ₁ (User), δ₂ (Project), δ₃ (Task) }
cd(AdminService) ⊇ { δ₁, δ₂, δ₃ } // Depende de todo, aunque solo usa User
// IRepository.java — interfaz gorda public interface IRepository {
    void createUser(User user);
    void createProject(Project project);
    void createTask(Task task);
    // ... más métodos
}

// AdminService.java — solo usa métodos de User public class AdminService {
    private IRepository repo;
    public void saveUser(User user) {
        repo.createUser(user); // Solo usa esto
    }
    // Depende de métodos que no usa (createProject, createTask)
}

Δ = 3 Dependencias innecesarias — AdminService cambia si cambia User, Project o Task.

✅ Solución Interfaces segregadas

Solución: Dividir IRepository en interfaces específicas: IUserRepository, IProjectRepository, ITaskRepository.

cd(IUserRepository) = { δ₁ }  |  cd(IProjectRepository) = { δ₂ }  |  cd(ITaskRepository) = { δ₃ }
cd(AdminService) = { δ₁ } // Solo depende de lo que usa
// IUserRepository.java — interfaz específica public interface IUserRepository {
    void createUser(User user);
    void deleteUser(User user);
}

// AdminService.java — solo depende de IUserRepository public class AdminService {
    private IUserRepository repo;
    public void saveUser(User user) {
        repo.createUser(user);
    }
}

Δ = 1 por servicio — cada servicio solo depende de los drivers que realmente usa.

🔹 DIP — Inversión de Dependencias

❌ Síntoma Servicio depende de MySQLRepositorio

Violación: El módulo de alto nivel (Servicio) depende de una implementación concreta (MySQLRepositorio).

(Servicio, MySQLRepositorio) ∈ D // Dependencia directa
cd(Servicio) ⊇ cd(MySQLRepositorio) // Cambios en MySQL afectan a Servicio
// Servicio.java — depende de implementación concreta public class Servicio {
    private MySQLRepositorio repo; // ❌ Dependencia concreta
    public void procesar() {
        repo.guardar();
    }
}

Δ = 1 Dependencia concreta — cambiar la base de datos obliga a modificar Servicio.

✅ Solución Servicio depende de IRepositorio

Solución: Introducir una interfaz IRepositorio. Ambos módulos dependen de la abstracción.

(Servicio, IRepositorio) ∈ D  ∧  (MySQLRepositorio, IRepositorio) ∈ D
cd(Servicio) ∩ cd(MySQLRepositorio) = ∅ // Aislados por la abstracción
// IRepositorio.java — abstracción public interface IRepositorio {
    void guardar();
}

// Servicio.java — depende de la abstracción public class Servicio {
    private IRepositorio repo; // ✅ Dependencia abstracta
    public void procesar() {
        repo.guardar();
    }
}

// MySQLRepositorio.java — implementación concreta public class MySQLRepositorio implements IRepositorio {
    public void guardar() { ... }
}

Δ = 0 Dependencias invertidas — Servicio no cambia si cambia la base de datos.
